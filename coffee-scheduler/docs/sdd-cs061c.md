# CS-061c invitation and audit hardening acceptance criteria

These criteria extend F61 for the invitation and audit slice. They pin behavior discovered while validating the production PostgreSQL path and complement the umbrella F61 criteria in `FEATURES.md`.

- **F61.ac7** — invitation conflict and redemption parity**: invitation creation for an existing tenant member or an existing pending invitation returns HTTP 409 through the production pooled repository; concurrent duplicate creates produce at most one success and the remaining requests receive the established conflict response. Normalize only the documented PostgreSQL conflict SQLSTATEs/messages; propagate unrelated database failures. A valid invitation redeems successfully on a freshly upgraded database, while unknown, expired, revoked, and already-used tokens keep the existing opaque failure response. The acceptance function remains SECURITY DEFINER with its pinned search path and grants, and its migration downgrade restores the previous definition.
- **F61.ac8** — shared anonymous invitation-accept throttling**: failed invitation acceptance attempts are counted atomically in durable PostgreSQL state shared across gateway processes and keyed only by canonical client IP. Distinct IPs remain independent; successful redemption clears only the successful IP bucket. The threshold-th attempt may proceed and subsequent attempts are blocked until exact lockout expiry; rolling-window cutoff semantics match the in-memory test model. Invalid IP/config values fail closed, state is bounded and expired entries are reclaimed, and application roles cannot read or mutate the throttle table or call its SECURITY DEFINER functions. The reversible migration upgrade/downgrade/upgrade leaves no stale throttle functions, tables, indexes, grants, roles, or columns.
