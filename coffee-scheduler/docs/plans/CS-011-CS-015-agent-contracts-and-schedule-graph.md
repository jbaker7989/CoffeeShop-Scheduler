# CS-011 and CS-015 development plan

CS-011 delivers versioned, authenticated A2A contracts and a real cross-framework exchange. CS-015 delivers a runnable, tenant-scoped workflow that takes a scheduling request through forecasting, labor compliance and CP-SAT to a reviewable draft. Both are P1 stories for the core Coffee Shop Scheduler. Start with the contract and dependency work in CS-011, build CS-015 against those contracts, then validate the Scheduler card against the completed graph before publishing it.

## Decisions to carry into the specs

- **Payroll/HCM stays in n8n.** Record the decision against F7, F12, F16 and F78 so CS-019 and CS-083 have one integration target. CS-083 still owns the versioned, reconciled export artifact. Schedule generation ends with a draft, and the export workflow consumes approved pay-period data through its later contract.
- **One callable skill per initial runtime card.** Use stable existing agent names and explicit skill IDs. Keep upstream protocol, card release, business payload and graph state versions distinct. Publish cards from the same validated configuration used to mount their handlers. Inventory, Prep and Loyalty remain clearly labeled design artifacts with no invocation URL, callable skills or served discovery endpoint.
- **Cross-framework path.** Use the Python LangGraph Scheduler as the A2A client and prototype Google ADK as the independently running Demand Forecast agent. ADK invokes a deterministic forecast tool or custom agent, with model inference handled by the existing forecasting code. Prove a real authenticated exchange on the selected release pair before adopting it. Try an isolated Forecast service environment if framework dependencies conflict. Require the recorded request to execute the ADK agent and validate its result through the Scheduler client.
- **One workflow entry point.** The authenticated Scheduler A2A operation and an operator smoke harness invoke the same graph service. Use the existing gateway principal/tenant binding when a browser-facing adapter is added. CS-031 owns the weekly grid and can consume the versioned draft contract later.
- **Fixed stage order.** LangChain typed tools wrap existing domain entry points. A small prompt and optional model router may classify supported intent or request clarification. Graph code alone controls the legal transitions and constructs tool arguments from validated data. A structured request runs without a model, model credentials or a live model dependency.
- **Calendar scope.** Specify an inclusive date range of one through seven calendar days using the currently supported business calendar. Begin with the existing tenant-wide store set and a server-authorized model version. Test dates around DST and effective-date boundaries. Where the existing domain contracts cannot represent a calendar or hour unambiguously, return a typed validation failure. Keep the broader employer-week decision with CS-089.

2. Add numbered acceptance criteria, edge cases and cross-references to F7 and F12 in a specification commit. Use the proposed IDs below after checking for collisions. Define the actual wire shapes, status/error mapping and fixture examples from the same specs. Record the payroll ownership decision in the relevant story and feature cross-references.
3. Run a disposable dependency spike using CI's Python 3.14 and current pins, including OR-Tools, FastAPI and telemetry imports. Choose one mutually supported released A2A protocol and transport, pin the SDK/framework versions and its schema reference, and save the exact install and import checks. Prefer a single request/response binding and only the interaction profile supported by all selected SDKs. Implement every operation mandatory for that profile. Test wire framing, discovery path and standard unsupported-operation behavior. Add dependencies to their owning manifests and run a clean CI-equivalent install. Use an isolated service environment for incompatible ADK dependencies or an explicitly supported service interpreter. Escalate a genuine interpreter or deployment change before depending on it.
4. Write and run tagged test-first commits before new production files for each logical unit. Confirm the failure is the missing behavior. Keep fixtures synthetic and versioned, with wire assertions independent of the implementation serializer.

## CS-011 implementation

### Runtime boundaries and minimum skills

| Card | Initial callable skill | Source and behavior |
| --- | --- | --- |
| Scheduler | Generate schedule draft | Call the CS-015 workflow. Return its versioned draft or typed failure. Keep discovery gated until the workflow passes the public contract. |
| Demand Forecast | Predict demand for date window | Resolve the approved tenant model and its pinned feature/taxonomy versions. Use `build_inference_rows` and `predict` for future windows. Return the F8 `ForecastSet` with no forecast-table mutation. |
| Labor Compliance | Evaluate a typed proposal | Resolve tenant and applicable snapshots, then call F10 `evaluate` with `persist=False`. Preserve binding failures, evaluation scope, verification status and premiums. Require genuine week, breaks or crew evidence where a requested verdict needs them. |
| Staff Comms | Preview a supported staff notification template | Render a bounded, versioned template preview for planned call-out communications. Use explicit template IDs and typed, non-PII parameters such as a store reference and local shift window. Return preview text and template version with no delivery or consent verdict. F15 owns recipient resolution, consent, inbound handling and SMS delivery. |

Validate the Staff Comms preview scope in the F7 spec before implementation. It is a small proposed runtime capability because the current agent contains a card and prompt scaffold. If product acceptance requires actual delivery for the initial card, sequence F15 before publishing Staff Comms and reflect the dependency in F7. Delivery eligibility stays with F15's consent workflow.

### Contract, authentication and transport

1. Implement one shared protocol adapter for envelope validation, error mapping and supported operation dispatch. Keep handlers thin and map each request to its owning business contract. Include a call correlation ID, explicit payload version and bounded request/response sizes. Reject unknown operations, missing or invalid structured parts, extra authority fields and out-of-contract dates or values before domain I/O.
2. Validate independently addressed endpoints at startup. Require configured trusted destinations and TLS in deployed environments. Allow loopback for explicitly isolated tests. Configure deadlines, reject automatic redirects and keep destinations independent of request text or returned discovery data. Declare only implemented media types and capabilities. Use the well-known discovery convention for the pinned profile, or its documented configured-card mechanism for shared infrastructure. Check the served card against the deployed routes and authentication.
3. Choose and document the service credential issuer, destination audience, authorized caller, allowed operations and tenant delegation. Use the existing verified principal at the ingress boundary, then a short-lived, audience-restricted service identity/delegation for the downstream call. Bind tenant and operation to verified claims or trusted server-side mappings. Require valid credential configuration, reject wrong audience or scope and derive every RLS session from authorized tenant context. Keep browser credentials, signing material, tokens, private network details and tenant information out of repository cards and discovery responses. Use destination-specific credentials. Validate capability access independently of protocol discovery.
4. Stabilize typed errors for authentication, authorization, invalid requests, unsupported protocol/skill, missing domain inputs, and transient service failures. Avoid exposing SQL, rule-snapshot internals, tenant existence, staff details or stack traces in errors. Propagate correlation identifiers and structured stage names in diagnostics.
5. Run discovery and invocation through a real Scheduler client and a separately started ADK Forecast worker. Assert negotiated version, authentication, remote tool execution and the exact F8 response the Scheduler deserializes. Repeat with an incompatible version and unavailable Forecast endpoint to prove that the client follows its error contract.

## CS-015 implementation

### Graph state and normal entry point

Use a LangGraph `StateGraph` with explicit nodes and typed outcomes. Define a versioned JSON representation for the request, stage outcomes, provenance, result and safe failure. Keep actor identity, service credentials, connection factories and dependencies in verified runtime context. Use an opaque server-generated run ID, tenant scope, canonical request fingerprint, approved model/feature/taxonomy versions, selected policy and stage sequence. Keep state compact with immutable artifact references or validated JSON where a later stage needs the values. Pin ISO date strings, timezone-aware timestamps, integer cents and the existing decimal string encoding at the wire boundary. Reject non-finite numbers and assert round-trip equality through both PostgreSQL JSONB and the selected A2A binding. Keep connections, credentials, raw employee records, compensation details and CP-SAT objects out of the checkpoint representation.

| Stage | Implementation and exit condition |
| --- | --- |
| Gather | Validate request kind, dates, size and authorized tenant/store/model scope before provisioning work. Pin the effective model and version inputs for the run, record the deadline and reject missing canonical records. Distinguish a legitimately closed day from missing hours or an unusable window. |
| Forecast | Call the real Forecast A2A skill once per attempt. Validate the returned F8 envelope again against the pinned versions, canonical locations, category vocabulary and expected open store-hour/category keys. A partial forecast, including a category omitted entirely, ends the run with a typed error. Derive expected keys independently from the payload. |
| Compliance | Prepare canonical tenant rule snapshots and the CS-016 per-assignment legality adapter. Resolve scope and effective dates in F10. Reuse immutable snapshot data per appropriate tenant/employer/employee and run. The local model-building loop uses the same deterministic F10 logic as the Labor Compliance service. A2A remains available to other callers for proposal evaluation. |
| Solve | Pass validated demand and tenant-bound legality into the existing CS-016 model, objective, bounded solve and decode path. Respect production gap/time limits and the remaining workflow deadline. Preserve typed infeasibility groups, no-incumbent errors and unacceptable-gap errors. |
| Present | Serialize the permitted projection of the existing `ScheduleOutput` with schema version, shifts, authorized economics, forecast provenance, solver quality and omissions. Preserve authoritative values and uncertainty. Identify the result as a draft with explicit compliance scope. A failed stage produces an error result without a schedule. |

### Fix known integration hazards before exposing the Scheduler skill

- **Forecast handoff.** `assemble_solver_inputs` currently queries persisted forecasts, and `run_schedule` assembles them internally. Add an explicit path taking a validated `ForecastSet` or prepared `SolverInputs`. Make the existing DB-backed path delegate to the same assembly/solve logic and preserve its calling convention. Prove the graph uses its returned forecast by seeding an older forecast for the identical model/window with different values. Compare direct runner and graph results on identical prepared inputs. Avoid write-and-read-back: prediction persistence inserts live keys and makes retries conflict with existing forecasts.
- **Forecast tenant isolation.** `model.predict` currently validates against the demo locations `{3, 5, 8}`. Resolve visible active stores and the model's taxonomy from tenant-scoped data; validate forecast hours against the same supported calendar contract on both sides. Test overlapping numeric store IDs in separate tenants plus a store outside the demo set. Verify the prediction path for a future window with no actual demand rows.
- **Compliance tenant binding.** `legality_from_compliance` currently sets the demo tenant UUID. Require the canonical tenant from a trusted scoped session/context. Keep snapshot reads and input assembly consistent on the same short read snapshot where practical, using the scoped-connection part of CS-090 if needed. Validate role, active transaction, RLS tenant and context agreement. Fetch what evaluation needs before the solve so long CPU work holds no DB transaction. Reopen a scoped connection for later checkpoint writes. Test two tenants sharing employee IDs but carrying opposite binding rules, including on a reused pooled backend.
- **Compliance coverage and readiness.** Candidate rules cover only the metrics CS-016 can decide per assignment. A filtered verdict, omitted objective term, absent breaks, incomplete week/crew data or unverified rule must remain visible whenever it affects interpretation. If the draft carries a whole-schedule verdict, derive it from complete authoritative facts using F10, including boundary-week history, breaks and crew. Missing facts yield an explicit incomplete review outcome. This graph may return a reviewable draft, and approval, publication and statutory verification remain owned by their existing workflows. Preserve the CS-021 legal-accuracy gate.
- **Calendar and coverage regressions.** Keep the CS-094 check over every open hour and avoid adding a second coverage matcher. Test closed weekdays, two-store windows, open/close boundaries and a partial expected demand grid. Exercise distinct open/close headcounts during validation. If the existing CS-096 matcher blocks the promised result, land its narrow fix before enabling the affected path. Keep weekly-rule semantics explicit and document the CS-089 limitation. Use the existing authoritative opens and timezone; reject inputs the F8/F11 contracts cannot represent, including ambiguous or unsupported local-hour shapes.

### Durability, retries and concurrent requests

1. Use the existing RLS-protected `langgraph_checkpoints` table and `CheckpointRepository` for versioned **application stage checkpoints**. For this linear graph, persist completed stages and resume through a trusted entry edge after validating the last committed state. Document the storage contract as application stage recovery, with the repository's `save/get_latest` methods as its starting point. Address workflows by tenant and run, with an explicit workflow/run key and preserved legacy agent rows if a reversible additive Alembic migration is necessary. Cover scope, sequence, predecessor and schema version. Test latest-stage selection using sequence order.
2. Use an atomic claim or compare-and-swap with an expiring attempt token and fencing so two workers cannot advance the same run. Use a short DB transaction for each claim or commit. Bind a caller idempotency key, if supported by the selected wire profile, to tenant, authorized owner and canonical request hash. Identical requests return the existing status/result. Reusing a key with changed data returns a conflict. A stale worker cannot finalize after takeover. Return success only after the terminal draft checkpoint commits. Validate run ownership and fresh authorization on every replay or resume.
3. Persist safe artifact/provenance references for completed work. Before reusing a checkpoint after restart, validate tenant/owner, schema, request fingerprint and relevant input versions. If canonical inputs affecting the next stage changed or a needed snapshot cannot be reproduced, restart from the earliest affected safe stage with a new attempt or return a typed stale-run result. Reject corrupt and unknown-version checkpoints explicitly. Establish bounded checkpoint size and retention for draft data, with scoped cleanup and minimal metadata.
4. Retry only explicitly classified transient failures in read-only/repeatable operations, using a small capped attempt count, backoff/jitter and one monotonic end-to-end deadline per attempt. Verify that configured proxy/A2A deadlines and the solver budget fit the same envelope. Treat auth, schema, invalid input, binding verdict failures, infeasibility, unacceptable gaps and configuration errors as terminal. Run CP-SAT outside the async event loop with bounded per-tenant/workflow concurrency. Avoid launching a second solve while a timed-out worker can still commit. Bound a repeated recovery attempt independently from model/router retry settings.
5. Emit low-cardinality stage/outcome, duration, retry and solver-quality telemetry using existing hooks. Include a correlation identifier and sanitized reason code. Keep schedule payloads, tokens, prompts with operational data, raw exceptions and employee identifiers out of logs and trace attributes. Include failed-checkpoint and stale-run cases in the operator runbook.

### Release gates

1. Run focused test-first files using `python3 -m unittest discover -s test -p 'test_cs011*.py'` and the corresponding `test_cs015*.py` pattern. Pin fixture dates, model versions and rule snapshots. Use bounded solver budgets and assert feasibility/objective invariants instead of relying on one arbitrary assignment when several optima tie.
2. Run a disposable PostgreSQL integration with two synthetic tenants, non-owner RLS roles, real Forecast/Scheduler processes and actual deterministic domain code. Start the forecasts with target-free inputs. Include one full-week smoke run at configured budgets and record wall time by stage, peak state size and output quality. Re-run the checkpoint integration through PgBouncer transaction pooling. Verify auth failures at the real transport boundary. If adding a migration, run upgrade → downgrade → upgrade and verify legacy checkpoint rows, grants, RLS, no leaked state and schema restoration. Use a scratch database for destructive tests.
3. Run project-wide unittest and CI-equivalent pytest, adjacent F8/F9/F10/F11/F30/F45/F60/F61/F68/F70 tests, changed-file Ruff, `git diff --check` and the existing spec traceability, test-first and review scripts against the PR base. Exercise gateway registration and manager regressions if gateway routing changes. Capture exact commands, pass/fail/skip counts, and environment gates. An in-memory checkpoint fixture or a skipped interoperability/database case cannot substitute for the release checks.
4. Ship in reviewable units ordered as spec → failing tests → implementation. Keep the shared A2A transport and F7 contract review distinct from the F12 graph and its persistence review. If CS-011 merges first, keep the Scheduler discovery capability disabled until the CS-015 verification. Update feature and backlog status with recorded evidence after each story meets its criteria. Run an end-to-end smoke test against the release configuration before enabling discovery.

The backlog estimates three development days per story. Re-estimate after the dependency spike and after confirming the Staff Comms scope and checkpoint schema. Those decisions, the real interop test and the full-week tenant-scoped smoke test determine the critical path.
