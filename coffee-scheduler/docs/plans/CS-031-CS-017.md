# CS-031 (weekly schedule view) + CS-017 (schedule explanation) — development plan

> Worktree `claude-cs031-cs017` off `origin/main`. Execution: **Codex writes code + tests, Claude
> validates on the host, commits+pushes on green, then bug-reviews and files any needed stories.**

## Context
With the solver (CS-016a–d), forecast (CS-014), auth (F60/F61), and the manager-app gateway+shell
(CS-030) all done, the next two stories put the solver's output in front of a manager and explain it:
**CS-031** renders the weekly roster; **CS-017** explains "why this person at this time," citing
`rule_eval_log` rule IDs. Both are read/explain surfaces — "no new scheduling logic."

**Blocking reality found in exploration (decides the shape of this plan):** nothing in the codebase
persists a generated schedule or writes `rule_eval_log` rows for drafts — `run_schedule` returns an
in-memory `ScheduleOutput`, drafts are ephemeral, and no production path calls `evaluate(persist=True)`.
So both stories would read empty tables. **Ratified decisions:**
1. **Add a minimal persistence step + seed** (not the full F74 publish lifecycle).
2. **`schedules.status` vocabulary = `draft` / `published` / `superseded`** (new CHECK; view shows `published`; regeneration soft-deletes the prior as `superseded`).
3. **CS-017 uses the real Anthropic API**, injected as a seam, strictly grounded.

Build order: **Foundation (persist + seed) → CS-031 → CS-017.**

## Foundation — persist the solver's output (shared unblocker)

Small, self-contained; both stories depend on it. Do NOT build publish/notify (F74/CS-078).

- **Migration `0026_cs031_schedule_status.py`** (chain from the real head — run `alembic heads`; it is
  `0025`, so `down_revision="0025"`). Add `CHECK (status IN ('draft','published','superseded'))` to
  `schedules.status`. Reversible downgrade (drop the constraint). Round-trip must pass
  (`test_migrations_roundtrip.py`). No new table.
- **`agents/scheduler/persist.py`** — `persist_schedule(conn, output: ScheduleOutput, *, tenant_id,
  location_id, week_start, status="published", solver_version) -> uuid`:
  - Maps `ScheduledShift` (`day`, `start_hour`/`end_hour` Decimal local, `employee_id`, `role`,
    `location_id`) → `shifts` rows: compute `start_at`/`end_at` as **tenant-local → UTC `timestamptz`**
    using `tenants.timezone` (IANA), assign `station_id` from the shift's station (or NULL if the solver
    didn't bind one — see risk), insert `shift_assignments` with `is_meal_break_covered` from the output.
  - Writes the parent `schedules` row; **soft-deletes any prior live schedule** for the same
    `(tenant_id, location_id, week_start)` by setting its `status='superseded'` + `deleted_at` (reuse
    `data_access.soft_delete`), so at most one live `published` schedule per (location, week).
  - **Persists per-assignment `rule_eval_log`**: for each assignment, call `compliance.engine.evaluate(
    proposal_with_shift_id, snapshot=<reused per employee/week>, persist=True, log=None)` so the engine
    writes `rule_eval_log` rows keyed by the now-persisted `shift_id` (this is the linkage CS-017 cites).
    Runs as `app_rw` in one tenant-scoped transaction. **Shift must be inserted before evaluate(persist)**
    (engine raises `ShiftNotPersisted` otherwise).
  - All under `data_access.session` (`app_rw`, transaction-local tenant GUC). Idempotent/rerunnable:
    a second persist of the same week supersedes the first, never duplicates a live schedule.
- **Seed** `scripts/seed_demo_schedule.py` (or extend the ETL seed): run the solver once for maven-demo
  for a fixed `week_start`, `persist_schedule(..., status="published")`, so the view + explanation have
  real data. Keep it idempotent (supersede-on-rerun).

## Story 1 — CS-031: Weekly schedule view (F31, P1, M)

**Goal:** read-only weekly roster in the manager app — shifts, station coverage, meal breaks; select a
shift → its `rule_eval_log` references; filters store/role/status/multi-week. **No grid mutation.**

### Gateway (`coffee-scheduler/api/`)
- **`api/db.py` → `GatewayDatabase.fetch_schedule(tenant_id, *, location_id, week_start) -> dict`** —
  mirror `fetch_stores` exactly: `with pool.connection() as conn, conn.transaction():
  open_session_context(conn, role="app_ro", tenant_id=tenant_id)` then read the **published** schedule +
  its shifts + assignments + stations for that (location, week). Prefer one SQL join; RLS + the
  soft-delete restrictive policy already hide other tenants and superseded rows (do **not** set
  `app.show_deleted`). Return typed rows (shift id, employee, role, station_id, start_at/end_at,
  is_meal_break_covered) + the station list for coverage. Use `app_ro` (read-only).
- **`api/db.py` → `fetch_shift_rule_evals(tenant_id, shift_id) -> list[dict]`** — read `rule_eval_log`
  by `(tenant_id, shift_id)` (RLS, `app_ro`): `rule_id, result, premium_cost_usd, reason(notes), agent`.
- **`api/app.py`** — `GET /schedule?location_id&week_start` and `GET /schedule/shift/{shift_id}/rules`,
  both `Depends(current_principal)` + `require_role("owner","manager")` + `require_email_verified`; pass
  only `principal.tenant_id` (never body/tenant from client); honor the `tenant_route` guard
  (`principal.tenant_id == route.tenant_id`). `location_id` is an app-level filter (RLS scopes tenant,
  not location) — validate it's an int; empty/unknown → empty grid, not 500.

### Manager app (Next.js, repo-root `coffee_shop/`)
- New route `app/(manager)/schedule/page.tsx` — async Server Component, **copy the `dashboard/page.tsx`
  template**: read `access_token` cookie, server-fetch `${apiBaseUrl}/schedule?...`, `cache:"no-store"`,
  `export const instant = false`; on 401 → `redirect("/session-refresh")`, other !ok → throw; render.
  Wire the existing inert `"Schedule"` nav item in `(manager)/layout.tsx` to `/schedule`.
- **Factor all shaping logic into a pure, unit-testable `.ts` module** (repo convention —
  `app/session-recovery.ts` + `node:test`): `app/schedule/grid.ts` with pure functions —
  `buildWeekGrid(shifts, tz)` (group by day × daypart in the **store/tenant timezone**, never UTC/browser),
  `stationCoverage(shifts, stations)` (staffed vs `staffed_by_role`; handle uncovered station + orphan
  `station_id`), `applyFilters(rows, {role,status})`, `weekNav(weekStart, ±1)`. Components stay thin.
- Filters: store (location_id), role, status, multi-week prev/next (re-query, no cache). **Empty state:**
  a week with no published schedule renders "No published schedule for this week," never throws (mirror
  the dashboard's `stores.length===0`). Shift-select panel calls `/schedule/shift/{id}/rules` and lists
  the rule IDs + reasons verbatim (no new prose — that's CS-017).

### F31 acceptance criteria to author (none exist) — add to FEATURES.md, tag tests `# spec: F31.acN`
- **ac1** `/schedule` returns only the caller-tenant's **published** live schedule for (location, week), RLS-scoped via `app_ro`; foreign/missing/tampered token → 401/403; no tenant/location spoof.
- **ac2** Shift times render in the **tenant timezone**; a shift near midnight UTC lands on the correct local day/daypart.
- **ac3** Grid shows per-day shifts (employee, role, station, start/end) + per-station coverage (staffed vs `staffed_by_role`, including uncovered stations) + per-assignment meal-break indicator.
- **ac4** Filters (store/role/status) and multi-week nav re-query and never leak another week/tenant; an empty/no-schedule week renders a graceful empty state, not an error.
- **ac5** Selecting a shift returns its `rule_eval_log` rows (rule_id + result + reason) for that shift only.
- **ac6** Superseded/soft-deleted schedules are never shown (restrictive policy respected; `app.show_deleted` never set).
- **ac7** Read-only: no endpoint mutates schedules/shifts/assignments.

### Tests
- Python: `test/test_cs031_schedule_api.py` — `TestClient(create_app(...fixture...))` + DB-gated
  rollback (`require_store_database`, seed-within-rollback, `raise Rollback`): auth→RLS, published-only,
  empty-week, no-spoof, shift-rules read. Mirror `test_api_foundation.py`.
- Frontend: `coffee_shop/test/schedule-grid.test.mts` (`node --test`) — pure-logic tests for
  `buildWeekGrid` (tz correctness, midnight-UTC edge), `stationCoverage` (uncovered/orphan), filters,
  week nav. No component/DOM tests (repo has none).

### CS-031 risks (bake into tests)
Timezone day-boundary (the headline — TIMESTAMPTZ → tenant-local); empty/no-published week; superseded
hidden; RLS `app_ro` scoping + never trust client tenant/location; orphan/uncovered `station_id`;
multi-week re-query (no stale cache); role gating (owner/manager); middleware does not presence-gate
`(manager)` — the page must self-fail-closed on 401 like the dashboard.

## Story 2 — CS-017: Schedule explanation layer (F13, P2)

**Goal:** given a shift/assignment, produce prose explaining it, **citing only** engine-produced
`rule_id`/reasons from `rule_eval_log` (or a live `judge()` fallback). The LLM explains; it never
invents rule IDs, numbers, verdicts, or facts.

### Service (`coffee-scheduler/agents/explanation/` — new read-only A2A-style package)
- **`explanation/grounding.py`** — pure, deterministic, no LLM: `gather_evidence(conn, tenant_id,
  shift_id) -> ShiftEvidence` reads `rule_eval_log` for the shift (RLS `app_ro`); if **no rows**
  (unpersisted/edge), fall back to re-running `compliance.engine.judge(snapshot, proposal_for_shift)` to
  get live `RuleResult`s. `ShiftEvidence` = the frozen set of `(rule_id, result, reason,
  premium_cost_usd?)` facts + category names from the taxonomy (CS-009), nothing else. This is the only
  thing the model may cite.
- **`explanation/service.py`** — `explain_assignment(conn, tenant_id, shift_id, *, model_client) ->
  Explanation`:
  - Build a strict prompt: system = the grounding contract ("explain using ONLY the provided facts; cite
    rule IDs exactly; never state a number or verdict not in the facts; if facts are insufficient, say
    so"); user = the serialized `ShiftEvidence`.
  - Call `model_client` (the injected seam) → prose.
  - **Post-validate (fail-closed):** every `rule_id` the output cites must be ∈ the evidence rule_ids
    (strip/reject unknowns); reject any numeric token not present in the evidence; never assert legal
    accuracy (surface `claims_legal_accuracy=False` / unverified caveat). Return `Explanation(text,
    cited_rule_ids, grounded: bool)`; on validation failure, return a safe deterministic fallback built
    from the evidence reasons (not the raw model text).
- **`explanation/model.py`** — the Anthropic seam: a thin `AnthropicExplainer` using the **official
  `anthropic` Python SDK**, `model="claude-sonnet-5-5"` (grounded summarization; cost-sensitive,
  per-shift), `thinking={"type":"adaptive"}`, `max_tokens≈1024`, `output_config={"effort":"low"}`. Reads
  `ANTHROPIC_API_KEY` from env; **if unset, the service degrades to the deterministic fallback** (no hard
  dependency on a key). Codex: load the `claude-api` skill and read `python/claude-api/README.md` for
  exact SDK usage; add `anthropic` to `requirements.txt`. The seam is a simple callable
  `(system:str, user:str) -> str` so tests inject a stub.

### Surface
- **Gateway endpoint** `GET /schedule/shift/{shift_id}/explain` on `api/app.py` (`current_principal` +
  `require_role("owner","manager")`), calling `explain_assignment`. Keep it **off the solver/draft hot
  path** (so solver tests stay deterministic). CS-031's shift panel can call it.

### F13 acceptance criteria to author (none exist) — tag tests `# spec: F13.acN`
- **ac1** Explanation cites only rule IDs present in that shift's evidence; a fabricated/unknown ID is stripped/rejected (never surfaced).
- **ac2** No number appears in the output that isn't in the evidence (premiums/hours/bounds come from engine facts verbatim or not at all).
- **ac3** Evidence is read RLS-scoped (`app_ro`) for the caller's tenant+shift only; cross-tenant/missing shift fails closed.
- **ac4** With no `rule_eval_log` rows, the live `judge()` fallback supplies evidence; with neither, a safe "insufficient evidence" response (never fabricated).
- **ac5** The layer never asserts legal accuracy (`claims_legal_accuracy=False` surfaced); unverified rules flagged.
- **ac6** Deterministic + testable: a stub model client drives tests; assertions are on grounding invariants (cited ⊆ evidence; no new numbers), not exact prose. No real API key needed in CI.
- **ac7** No new scheduling/legality logic — explanation only; category names come from the taxonomy version.

### Tests
- `test/test_cs017_explanation.py` — stdlib unittest. Inject a **stub model client** returning canned
  text (incl. an adversarial one that cites a bogus rule_id and an invented number) and assert the
  validator strips/rejects them; DB-gated rollback test for `gather_evidence` (seed a shift +
  rule_eval_log within rollback, read it back); the `judge()`-fallback path; the no-key fallback path.
  Never calls the real API.

### CS-017 risks (bake into tests)
LLM inventing rule IDs → validate ⊆ evidence; LLM citing numbers → strip non-evidence numerics;
un-grounded/legal-accuracy claims → caveat + `claims_legal_accuracy=False`; empty rule_eval_log →
`judge()` fallback; RLS scoping of `rule_eval_log`/snapshot reads; determinism → injected stub in tests;
keep the LLM out of the solver hot path; no API key in CI (fallback path).

## Shared conventions
stdlib `unittest` (no pytest); `# spec: F*.acN` tags for the traceability gate; DB-gated tests
`@unittest.skipUnless(...)` + `with conn.transaction(): … raise Rollback` (nothing persists), never a
shared/prod DB; `TENANT_ID=00000000-…-0001`; reads via `data_access.session` (`app_ro` for reads,
`app_rw` for the persist helper), never a Python tenant filter; migration reversible + round-trip;
Ruff via `ruff.toml` on changed files; frontend `node --test` pure-logic modules.
